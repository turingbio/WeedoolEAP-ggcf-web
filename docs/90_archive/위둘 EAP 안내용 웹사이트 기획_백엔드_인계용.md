# 위둘 EAP 안내용 웹사이트 기획

## 0. 페이지 구성

화면은 둘이다. 기관코드 확인 화면이 먼저 나오고, 확인되면 내부 페이지로 들어간다. 내부 페이지는 위에서 아래로 내려가며 보는 랜딩 페이지다.

```
[기관코드 확인 화면]           [랜딩 페이지]
┌────────────────────┐        ┌──────────────────────────┐
│ ① 기관코드         │ ─확인→ │ ② 위둘 소개              │
└────────────────────┘        │ ③ 익명성                 │
                              │ ④ 매뉴얼 다운로드        │
                              │ ⑤ 계정 발급              │
                              │ ⑥ 계정 정보 저장(PNG)    │
                              │ ⑦ 앱 설치                │
                              │ ⑧ 매뉴얼 다운로드        │
                              ├──────────────────────────┤
                              │ 푸터: 문의처             │
                              └──────────────────────────┘
```

**화면 주소**

| 상황                                   | 주소                                         |
| -------------------------------------- | -------------------------------------------- |
| QR로 들어올 때 (기관코드 확인 화면)    | `https://{도메인}/verify?orgCode={기관코드}` |
| 기관코드 확인 후 (랜딩 페이지)         | `https://{도메인}/welcome`                   |
| 확인하지 않고 `/welcome`으로 들어올 때 | `/verify`로 보냄                             |
| 도메인만 입력해 `/`로 들어올 때        | `/verify`로 보냄                             |

- 루트(`/`)는 나중에 다른 용도의 페이지로 쓸 수 있도록 비워 두고, 지금은 `/verify`로 보내기만 한다
- 기관코드 확인 후에는 랜딩 페이지 주소에 파라미터를 붙이지 않는다. 확인 상태는 브라우저 안에 저장해 새로고침해도 유지한다
- 랜딩 페이지 구성은 추후 변경이 가능하고, 디자인 및 UX 라이팅은 프론트엔드에서 담당한다

## 1. 범위

웹사이트가 서버에 요청하는 API는 두 개다.

| #   | 용도             | 메서드·경로            |
| --- | ---------------- | ---------------------- |
| 1   | 기관코드 확인    | `POST /api/org/verify` |
| 2   | 계정 발급·재발급 | `POST /api/accounts`   |

서버를 거치지 않는 기능:

- 매뉴얼 PDF: 프론트엔드 정적 파일
- 계정 정보 PNG: 브라우저에서 생성
- 스토어 링크·설치 QR 이미지: 프론트엔드 정적 자원

---

## 2. 공통 규칙

### 가. 요청·응답

- 형식: JSON, `Content-Type: application/json; charset=utf-8`
- 인증: 없음
- 기본 주소: 환경 변수로 받는다 `NEXT_PUBLIC_API_BASE_URL`
  - 프론트엔드는 `기본 주소 + /api/org/verify`처럼 문자열을 이어 붙여 호출한다
  - **기본 주소는 `/api`와 끝의 `/` 없이 전달한다 (예: `https://api.example.com`)**

### 나. CORS

- 쿠키·인증 정보는 보내지 않는다
- 허용 Origin

| 환경 | Origin                                              |
| ---- | --------------------------------------------------- |
| 개발 | `http://localhost:3000`, `http://192.168.0.88:3000` |
| 운영 | 도메인 확정 후 전달                                 |

### 다. 개인정보

- 요청에 이름·이메일·연락처·부서·성별·연령 등 개인을 식별할 수 있는 값을 담지 않는다
- 서버는 발급한 계정과 개인을 잇는 정보를 저장하지 않는다
- 아이디 찾기·비밀번호 찾기 API는 없다

### 라. 에러 응답 형식 `[가정]`

```json
{
  "error": {
    "code": "INVALID_ORG_CODE",
    "message": "기관코드가 올바르지 않습니다"
  }
}
```

- 프론트엔드는 `code`로 분기한다. `code` 형식은 백엔드 컨벤션에 따라 변경될 수 있다.
- `message`는 화면에 그대로 쓰지 않는다. 화면 문구는 프론트엔드 파일이 정한다

### 마. 에러 코드 `[가정]`

| code               | HTTP | 뜻                                                 | 화면 처리                         |
| ------------------ | ---- | -------------------------------------------------- | --------------------------------- |
| `INVALID_ORG_CODE` | 400  | 계정 발급 요청의 기관코드가 틀리거나 존재하지 않음 | 「기관코드를 다시 확인해 주세요」 |
| `SERVER_ERROR`     | 500  | 서버 내부 오류                                     | 「잠시 후 다시 시도해 주세요」    |

- 기관코드 확인 API는 이 에러 코드를 쓰지 않고 `valid` 값으로 답한다 (3장)
- 응답이 없거나 네트워크 오류가 나면 프론트엔드는 `SERVER_ERROR`와 같이 처리한다.
- 표에 없는 코드나 HTTP 상태(예: 429)도 프론트엔드는 `SERVER_ERROR`와 같이 처리한다.
- 백엔드 컨벤션에 따라 에러코드가 달라지거나 그 수가 늘어날 수 있다. 다만 프론트엔드에서 처리하는 로직은 똑같다.

## 3. 기관코드 확인

`POST /api/org/verify`

### 요청

| 필드      | 타입   | 필수 | 설명           |
| --------- | ------ | ---- | -------------- |
| `orgCode` | string | 예   | 기관코드 6글자 |

```json
{ "orgCode": "GGCF26" }
```

### 응답

**200 OK** — 기관코드 판정 결과는 `valid`로 답한다

| 필드    | 타입    | 설명                                                             |
| ------- | ------- | ---------------------------------------------------------------- |
| `valid` | boolean | `true`: 유효한 기관코드 / `false`: 형식이 틀리거나 존재하지 않음 |

```json
{ "valid": true }
```

```json
{ "valid": false }
```

**500 Internal Server Error**

```json
{ "error": { "code": "SERVER_ERROR", "message": "..." } }
```

### 규칙

- 기관코드는 영문 대문자·숫자 6글자다
- 기관코드는 암복호화하지 않는다
- 기관코드는 재단당 하나다

### 호출 시점

- 기관코드 확인 화면(`/verify`)에서 입력칸에 6글자가 채워지는 즉시
- QR 주소 `/verify?orgCode={기관코드}`로 들어와 값이 자동으로 채워진 경우도 같다

## 4. 계정 발급·재발급

`POST /api/accounts`

### 요청

| 필드      | 타입   | 필수 | 설명                   |
| --------- | ------ | ---- | ---------------------- |
| `orgCode` | string | 예   | 확인을 통과한 기관코드 |

```json
{ "orgCode": "GGCF26" }
```

### 응답

**201 Created**

| 필드              | 타입   | 설명                             |
| ----------------- | ------ | -------------------------------- |
| `accountId`       | string | 무작위 아이디                    |
| `accountPassword` | string | 무작위 비밀번호                  |
| `expiresAt`       | string | 만료 시각, ISO 8601, 시간대 포함 |

```json
{
  "accountId": "wd7k3m9p",
  "accountPassword": "h4t8w2qz",
  "expiresAt": "2026-09-14T15:40:00+09:00"
}
```

**400 Bad Request** — 기관코드가 유효하지 않음

```json
{ "error": { "code": "INVALID_ORG_CODE", "message": "..." } }
```

**500 Internal Server Error**

```json
{ "error": { "code": "SERVER_ERROR", "message": "..." } }
```

### 만료 규칙

- `expiresAt` = 발급 시점 + TTL
- TTL 기획값은 10분이다. 값은 서버 설정으로 두고, 프론트엔드는 TTL 값을 모른다
- TTL은 발급부터 앱 첫 로그인까지만 적용된다. 첫 로그인에 성공한 계정은 만료되지 않는다
- 첫 로그인 없이 `expiresAt`이 지나면 그 계정으로는 로그인할 수 없다
- 프론트엔드는 `expiresAt`을 그대로 받아 표시하고, 이 시각이 지나면 재발급 버튼을 보여 준다

### 재발급 규칙

- 재발급은 같은 `POST /api/accounts`를 다시 호출한다
- 재발급은 이전 계정과 관계없이 새 계정을 만든다. 요청에 이전 계정 정보를 담지 않는다
- 재발급 횟수 제한은 없다

### 아이디·비밀번호 형식

고연령 이용자가 옮겨 적기 쉽도록 헷갈리는 글자(0·o·1·l·i)를 뺀다.

| 필드              | 형식                     |
| ----------------- | ------------------------ |
| `accountId`       | `wd` + 소문자·숫자 6자리 |
| `accountPassword` | 소문자·숫자 8자리        |

## 5. 앱 쪽 참고 (웹사이트 범위 밖)

- 만료된 임시 계정으로 앱 로그인을 시도하면 앱이 안내 문구를 보여 준다
- 이 문구와 앱 로그인 API는 이 문서에서 정하지 않는다

---

## 6. 백엔드 참고 사항

웹사이트 동작에는 영향이 없다. 서버 설계에서 검토할 만한 항목이며, 적용 여부와 방식은 백엔드가 정한다.

| 항목           | 참고 내용                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 남용 대응      | 인증이 없고 재발급 제한도 없다. 기관코드는 QR과 사내 익명 창구에 공개되므로, 코드만 알면 계정을 계속 만들 수 있다. 요청 속도 제한 등을 검토할 수 있다 |
| 만료 계정 정리 | 첫 로그인 없이 만료된 계정을 비활성화할지 삭제할지, 언제 정리할지                                                                                     |
| 아이디 중복    | `accountId`의 경우의 수는 31⁶(약 8.9억)이다. 발급할 때 중복을 어떻게 막을지                                                                           |

## 7. 프론트엔드 mock 규칙

실제 서버가 준비되기 전까지 프론트엔드는 API mocking으로 개발한다.

| 입력                                           | 결과                                                  |
| ---------------------------------------------- | ----------------------------------------------------- |
| 유효 기관코드 (환경 변수로 지정, 예: `A1B2C3`) | 확인 200 `valid: true`, 계정 발급 201                 |
| 그 밖의 6글자                                  | 확인 200 `valid: false`, 계정 발급 `INVALID_ORG_CODE` |
| 오류 재현용 기관코드 (예: `ERR500`)            | `SERVER_ERROR`                                        |

- mock TTL은 10분이며, 만료 화면을 확인하기 위해 짧게 바꿀 수 있다
- mock 계정은 4장의 형식으로 무작위 생성한다
