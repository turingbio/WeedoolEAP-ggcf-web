# 8. 화면 구성과 UX 라이팅

목표: 7번까지 만든 화면의 구성과 문구를 `docs/21_UX_문구.md` v0.8에 맞춘다. 디자인을 입히기 전에 무엇이 어디에 있고 무슨 문구를 쓰는지부터 고정한다.

문구가 흔들리면 디자인이 흔들린다. 글자 수가 달라지면 줄 수가 달라지고, 줄 수가 달라지면 카드 높이와 여백이 전부 다시 계산된다. 그래서 디자인보다 이 단계를 먼저 한다.

---

## 8-1. 기준 문서

| 문서 | 무엇을 가져오나 |
| --- | --- |
| `docs/21_UX_문구.md` v0.8 | 섹션 순서, 배치도, 섹션별 문구 전체 |
| `docs/11_seed.yaml` | 화면 구성 제약, 수락 기준 |
| `PRODUCT.md` | 사용자상, 용어, UX 라이팅 원칙 |

셋이 다르면 **문구는 21번 배치도**를 따른다. 배치도에 적힌 사용자 문구는 이미 결정된 사항이다. 어색해 보여도 임의로 고치지 않고, 고칠 이유가 있으면 먼저 묻는다.

## 8-2. 화면 구성 확정

### 이 순서인 이유

섹션 순서는 취향이 아니라 **의심을 걷어내는 순서**다. 이 사이트의 이용자는 상담이라는 민감한 목적으로 처음 들어오고, 머릿속 질문이 정해진 차례로 떠오른다.

| 이용자의 속마음 | 답하는 섹션 |
| --- | --- |
| 이게 뭐지? 왜 나한테 왔지? | 01 `hero` — 기관이 보낸 것이라고 알린다 |
| 무슨 앱인데? | 02 `intro` — 기능 카드 4개 |
| 회사가 내 상담 내용을 보는 거 아니야? | 03 `anonymity` — 카드 3개 |
| (안심했으니) 그럼 해볼게 | 04 `account` — 계정 발급 |
| 받았는데 이제 뭘 하지? | 05 `process` — 다섯 단계 |
| 앱은 어디서 받아? | 06 `install` — QR·스토어·매뉴얼 |
| 아직 못 물어본 게 있는데 | 07 `faq` — 질문 7개 |

핵심은 **04가 03 뒤에 있다는 점**이다. 안심시키기 전에 계정부터 내밀면, 개인정보를 요구받는다고 오해한 사람이 그 자리에서 떠난다. 반대로 익명성 설명이 너무 앞에 있으면 무슨 서비스인지도 모르는 채 안심 문구부터 읽게 된다. 02와 04 사이에 03을 두는 배치는 이 두 실패를 함께 피한다.

07 FAQ가 맨 뒤인 것도 같은 이유다. FAQ는 흐름을 타지 못한 사람을 위한 안전망이지 본 흐름이 아니다. 앞에 두면 "문제가 많은 서비스"라는 인상을 준다.

**다른 안내 사이트에도 그대로 쓸 수 있는 규칙.** 행동을 요구하는 섹션(가입, 발급, 결제) 바로 앞에는 그 행동의 가장 큰 거부감을 해소하는 섹션을 둔다. 거부감이 무엇인지는 서비스마다 다르다. 이 서비스에서는 익명성이었다.

### 한 페이지인 이유

일곱 단계를 일곱 주소로 나누지 않고 `/welcome` 한 페이지에 세로로 쌓았다.

- 고연령 이용자가 뒤로 가기를 누르면 흐름의 어디로 돌아가는지 예측하기 어렵다. 스크롤은 되돌아가도 맥락이 유지된다
- 계정을 화면 state로만 들고 있어서, 페이지를 옮기는 순간 계정이 사라진다. 저장하지 않는다는 원칙이 곧 한 페이지 구조를 요구한다
- QR로 한 번 들어와 한 번 끝내고 나가는 일회성 통과가 기본이다. 재방문 동선을 위한 주소 체계가 필요 없다

반대로 `/verify`는 분리했다. 기관코드 확인은 **통과 여부가 갈리는 관문**이라 나머지와 성격이 다르고, QR 주소(`/verify?orgCode=...`)가 밖에서 들어오는 입구이기 때문이다.

### 6번 문서와 달라진 곳

6번 문서에서 만든 registry는 v0.5 기준이다. v0.8에서 섹션이 셋 늘고 둘 사라졌다. 여기서 맞춘다.

| 변경 | 섹션 | 이유 |
| --- | --- | --- |
| 추가 | `hero` | 편지가 도착하는 첫 화면. 애니메이션이 들어간다 |
| 추가 | `process` | 앱 이용 흐름 5단계. v0.7에서 신설 |
| 추가 | `faq` | 자주 묻는 질문 7개. v0.7에서 신설 |
| 삭제 | `manual-top`, `manual-bottom` | 매뉴얼 버튼을 `install` 한 곳으로 합쳤다 |
| 섹션에서 내림 | `credential-image` | 독립 섹션이 아니라 `account` 안의 패널이 되었다 |
| 삭제 | 긴급 연락처 | v0.6에서 뺐다 |

`credential-image`는 폴더가 남아 있지만 registry에는 없다. `AccountSection`이 `CredentialPanel`을 직접 불러 쓴다. 계정 카드와 발급 버튼이 한 화면에 붙어 있어야 「발급 → 저장」이 한 흐름으로 읽히기 때문이다.

### registry

`src/sections/registry.ts`

```ts
export const landingSections: SectionDefinition[] = [
  { id: 'hero', Component: HeroSection, enabled: true },
  { id: 'intro', Component: IntroSection, enabled: true },
  { id: 'anonymity', Component: AnonymitySection, enabled: true },
  { id: 'account', Component: AccountSection, enabled: true },
  { id: 'process', Component: ProcessSection, enabled: true },
  { id: 'install', Component: InstallSection, enabled: true },
  { id: 'faq', Component: FaqSection, enabled: true },
];
```

### 코드 읽기

- 배열 순서가 곧 화면 순서다. 21번 문서 1-2장의 표와 이 배열이 한 줄씩 대응한다
- id는 폴더 이름과 같게 둔다. `process` 섹션은 `src/sections/process/`에 있다. 문서에서 `process`라 부르는데 코드가 `app-flow`인 상태가 한동안 있었고, 그때 섹션을 찾는 데 시간이 걸렸다
- `visibleWhen`을 쓰는 섹션이 지금은 없다. 계정 유무로 갈리던 `credential-image`가 `account` 안으로 들어갔기 때문이다
- Header와 Footer는 registry에 없다. `src/app/welcome/page.tsx`가 `<LandingSections />` 바깥에서 직접 그린다

### 화면 두 개의 관계

```
QR 스캔 ──▶ /verify ──▶ (sessionStorage에 기관코드 저장) ──▶ /welcome
                              │
                              └─ 기관코드 없이 /welcome 접근 → /verify로 되돌림
```

`/welcome`은 한 페이지다. 섹션이 일곱 개라도 주소는 하나이고, 이동은 스크롤로 한다. 단계마다 주소를 나누지 않는 이유는 고연령 이용자가 뒤로 가기로 흐름을 잃지 않게 하기 위해서다.

### 확인

```bash
# registry의 id 순서를 눈으로 대조한다
grep -o "id: '[a-z-]*'" src/sections/registry.ts
```

| # | 할 일 | 기대 결과 |
| --- | --- | --- |
| 1 | 위 명령 실행 | `hero intro anonymity account process install faq` 순서 |
| 2 | `src/sections/` 폴더 목록 | registry의 id와 폴더 이름이 하나씩 짝을 이룸 |
| 3 | `/welcome`에서 매뉴얼 버튼 세기 | 앱 설치 섹션에 하나뿐 |
| 4 | 계정 발급 후 만료 시각 지나기 | 재발급 안내나 버튼이 나타나지 않음. 새로고침하면 발급 전 상태 |
| 5 | 개발자 도구 Elements에서 `<section id="...">` | id가 겹치지 않음 |

## 8-3. 문구가 사는 곳

문구는 컴포넌트 안에 직접 쓰지 않는다. 두 곳에만 둔다.

| 위치 | 담는 것 |
| --- | --- |
| `src/sections/<섹션 id>/content.ts` | 그 섹션에서만 쓰는 문구 |
| `src/content/common.ts` | 여러 곳에서 쓰는 문구, 푸터, 공통 라벨 |

이렇게 두면 문구만 고칠 때 컴포넌트를 건드리지 않아도 되고, 21번 문서와 한 줄씩 맞춰 보기도 쉽다.

섹션 제목은 **라벨·제목·설명** 세 줄 구조다. 산타 토익 랜딩을 참고해 v0.7에서 정했다.

```ts
export const processContent = {
  label: '프로세스',
  title: '위둘 EAP, 다섯 단계로 사용해요',
  // ...
} as const;
```

## 8-4. 문체 원칙

| 항목 | 규칙 |
| --- | --- |
| 어미 | 해요체와 합니다체를 함께 쓴다. 안내와 권유는 해요체, 사실 확인과 FAQ 답변은 합니다체 |
| 제목 | 라벨·제목·설명 세 층. 라벨과 설명은 필요한 섹션에만 둔다 |
| 과장 | 제목에 느낌표와 과장 표현(압도적인, 최고의)을 쓰지 않는다 |
| 설명 | 동작 원리를 설명하지 않는다. 버튼만으로 뜻이 통하면 설명 문구를 두지 않는다 |
| 불가 안내 | 안 되는 일은 짧은 이유를 붙여 완곡하게 쓴다 |
| 용어 | 기관코드, 계정, 기관, 운영사, 사용자 매뉴얼로 고정한다 |
| 약속 | 계약 5개 조항의 뜻을 넘어서는 약속을 하지 않는다. 개선율 수치(예: 우울감 82% 개선)를 쓰지 않는다 |
| 다루지 않는 것 | 위기 시 비밀보장 예외, 전문 상담사 연결 기능 |

어미를 하나로 통일하지 않은 이유가 있다. 해요체만 쓰면 FAQ의 "알 수 없습니다"가 "알 수 없어요"가 되는데, 익명성처럼 단정해야 신뢰가 생기는 답변에서는 어조가 물러진다. 반대로 합니다체만 쓰면 권유하는 자리가 딱딱해진다. **단정할 자리는 합니다체, 권하는 자리는 해요체**가 기준이다.

`FAQ 4번` 답변이 좋은 예다. "복구 불가"라고 끊지 않고, 이유와 대안을 함께 준다.

> 비식별 계정이라 다시 찾아 드리기 어려운 점 양해 부탁드립니다. 페이지를 새로고침하시면 새 계정을 발급받으실 수 있어요. 다만 이전 기록은 이어지지 않아요.

## 8-5. 상태별 문구

정상 화면만 있는 게 아니다. 아래 상태의 문구가 모두 있어야 9번 디자인 단계에서 화면을 그릴 수 있다.

| 화면 | 상태 | 있어야 할 문구 |
| --- | --- | --- |
| `/verify` | 기본 / 확인 중 / 코드 오류 / 연결 오류 | 입력 안내, 버튼 라벨, 오류 문구 |
| `account` | 발급 전 / 발급 중 / 발급 후 / 오류 | 버튼 라벨, 만료 시각 안내, 저장 안내, 재시도 |
| `install` | 기본 | QR 설명, 스토어 버튼, 매뉴얼 버튼 |
| `faq` | 접힘 / 펼침 | 질문 7개와 답변 |

21번 문서 4장의 표에 상태별 문구가 이미 정리되어 있다. 빠진 상태가 있으면 지어내지 말고 미결로 올린다.

## 8-6. 미결 항목 다루기

미결은 21번 문서 6장에만 적는다. 이 가이드에 옮겨 적으면 둘이 어긋나고, 그때부터 어느 쪽이 최신인지 아무도 모른다. 여기서는 **성격별로 어떻게 다루는지**만 정한다.

| 성격 | 이 단계에서 할 일 | 예 |
| --- | --- | --- |
| 문구가 아직 안 정해짐 | 임시 문구를 넣고 `TODO`로 표시한 뒤 확정을 요청한다 | 요금 관련 답변 |
| 자산이 아직 없음 | 자리와 크기만 잡아 둔다. 9번 에셋 목록에 올린다 | 앱 캡처 이미지 |
| 나중에 교체 예정 | 기존 파일을 그대로 쓴다. 교체해도 구조가 안 바뀌게 경로만 고정한다 | 사용자 매뉴얼 PDF |
| 구현 후 판단 | 일단 만들고 실제 화면에서 정한다 | Hero 애니메이션 유지 여부 |

미결을 임의로 확정하지 않는다. 대신 비어 있는 자리가 화면에서 보이게 둔다. 회색 상자가 남아 있으면 누구나 묻지만, 그럴듯한 임시 문구를 채워 두면 아무도 묻지 않은 채 그대로 배포된다.

21번 문서가 자주 바뀐다. 이 단계를 시작할 때 **6장 미결 항목과 2장 문체 원칙을 다시 읽는다.** 이전에 읽은 기억으로 진행하면 확정된 항목을 미결로 두거나, 바뀐 문체 규칙을 놓친다.
