- 작성일: 2026-09-14
- 수정일: 2026-09-22
- 상태: **실제 서버 기준으로 갱신** (2026-09-22)
- 근거: `https://lifeapi.weedool.com:8071/api-docs` (Weedool Life API - Manager), `docs/11_seed.yaml` (revision 7)
- 대상: 프론트엔드 구현자와 백엔드 담당자
- 표기: `[확인 필요]` 서버 동작을 실제로 확인하지 못한 항목

v0.3까지는 프론트엔드 mock을 기준으로 작성한 안이었다. v0.4부터는 이미 구현된 서버를 기준으로 하고, 프론트엔드가 서버에 맞춘다.

---

## 1. 범위

웹사이트가 서버에 요청하는 API는 두 개다.

| #   | 용도             | 메서드·경로                            |
| --- | ---------------- | -------------------------------------- |
| 1   | 기관코드 확인    | `GET /orgs/v1/{orgCd}/validate`        |
| 2   | 계정 발급·재발급 | `POST /non-identify/accounts/v1/issue` |

서버를 거치지 않는 기능:

- 매뉴얼 PDF: 프론트엔드 정적 파일
- 계정 정보 PNG: 브라우저에서 생성
- 스토어 링크·설치 QR 이미지: 프론트엔드 정적 자원

## 2. 공통 규칙

### 가. 요청·응답

- 형식: JSON, `Content-Type: application/json; charset=utf-8`
- 인증: 없음. 두 API 모두 인증 없이 호출한다
- 기본 주소: 환경 변수로 받는다 `NEXT_PUBLIC_API_BASE_URL`
  - 운영 주소는 `https://lifeapi.weedool.com:8071`이다
  - **끝의 `/` 없이 전달한다.** 프론트엔드가 `기본 주소 + /orgs/v1/...`으로 이어 붙인다

### 나. 응답 래퍼

성공과 실패 모두 같은 형태로 감싸서 온다.

```json
{
  "code": 200,
  "message": "Success",
  "data": {},
  "detailCode": null
}
```

| 필드         | 뜻                                     |
| ------------ | -------------------------------------- |
| `code`       | HTTP 상태 코드 또는 내부 코드          |
| `message`    | 서버 메시지. 화면에 그대로 쓰지 않는다 |
| `data`       | 실제 응답 본문. 실패하면 `null`        |
| `detailCode` | 실패 상세 코드. 성공하면 `null`        |

프론트엔드는 `data`만 꺼내 쓰고, 실패는 `detailCode`로 분기한다. `message`는 화면에 쓰지 않는다. 화면 문구는 프론트엔드 문구 파일이 정한다.

### 다. CORS

- 쿠키·인증 정보는 보내지 않는다
- **2026-09-22 기준 허용되지 않은 상태다.** `Origin` 헤더를 붙여 요청하면 403이 돌아온다. 아래 주소를 서버에 등록해야 브라우저에서 호출할 수 있다

| 환경 | Origin                                    |
| ---- | ----------------------------------------- |
| 개발 | `http://localhost:3000`                   |
| 개발 | `http://192.168.0.*:3000` (실기기 점검용) |
| 운영 | 도메인 확정 후 전달                       |

`POST /non-identify/accounts/v1/issue`는 `Content-Type: application/json`을 쓰므로 브라우저가 preflight(`OPTIONS`)를 먼저 보낸다. `OPTIONS` 응답도 허용되어야 한다.

### 라. 개인정보

- 요청에 이름·이메일·연락처·부서·성별·연령 등 개인을 식별할 수 있는 값을 담지 않는다
- 서버는 발급한 계정과 개인을 잇는 정보를 저장하지 않는다
- 아이디 찾기·비밀번호 찾기 API는 없다

### 마. 에러 코드

Swagger 문서에 적힌 것 중 이 웹사이트에서 만날 수 있는 것들이다. 전부가 아닐 수 있다.

| detailCode    | HTTP | 뜻                   | 화면 처리                          |
| ------------- | ---- | -------------------- | ---------------------------------- |
| `CMN001`      | 404  | 존재하지 않는 경로   | 「문제가 생겼어요…」               |
| `CMN002`      | 400  | 잘못된 입력          | 「기관코드를 다시 확인해 주세요」  |
| `ORG003`      | 404  | 존재하지 않는 기관   | 「기관코드를 다시 확인해 주세요」  |
| `CONTRACT001` | 404  | 계약하지 않은 기관   | 「기관코드를 다시 확인해 주세요」  |
| `CONTRACT004` | 400  | 유효하지 않은 계약   | 「문제가 생겼어요…」 `[확인 필요]` |
| `CONTRACT005` | 400  | 계약 인원 초과       | 「문제가 생겼어요…」 `[확인 필요]` |
| `CONTRACT008` | 400  | 서비스 기간이 아님   | 「문제가 생겼어요…」 `[확인 필요]` |
| `TERMS001`    | 409  | 약관이 존재하지 않음 | 「문제가 생겼어요…」               |

- 응답이 없거나 네트워크 오류가 나면 프론트엔드는 서버 오류와 같이 처리한다
- 표에 없는 코드도 서버 오류와 같이 처리한다
- 기관코드 확인 API는 에러 코드를 쓰지 않고 `exists` 값으로 답한다 (3장)

`[확인 필요]` 표시가 붙은 셋은 이용자가 기관코드를 고쳐도 풀리지 않는다. 계약 인원이 찼거나 서비스 기간이 아닌 상황이라 「잠시 후 다시 시도해 주세요」가 맞는 안내가 아니다. 이 상황에 어떤 문구를 보여 줄지는 `docs/21_UX_문구.md`에서 정한 뒤 코드로 옮긴다.

## 3. 기관코드 확인

`GET /orgs/v1/{orgCd}/validate`

### 요청

| 위치 | 이름    | 타입   | 설명                        |
| ---- | ------- | ------ | --------------------------- |
| 경로 | `orgCd` | string | 기관코드. 영문·숫자 6~8글자 |

```
GET /orgs/v1/GGCF26/validate
```

### 응답

**200 OK** — 기관이 없어도 200이다. 판정은 `data.exists`로 한다

| 필드                        | 타입     | 설명                                                |
| --------------------------- | -------- | --------------------------------------------------- |
| `data.orgCd`                | string   | 조회한 기관코드                                     |
| `data.exists`               | boolean  | `true`: 존재하는 기관                               |
| `data.orgType`              | string   | `CORPORATE` \| `UNIVERSITY`. 웹사이트는 쓰지 않는다 |
| `data.requiredAqCategories` | string[] | 필수 심화 문진 카테고리. 웹사이트는 쓰지 않는다     |

```json
{
  "code": 200,
  "message": "Success",
  "data": {
    "orgCd": "GGCF26",
    "exists": true,
    "orgType": "CORPORATE",
    "requiredAqCategories": ["JOB_STRESS", "DEPRESSION"]
  },
  "detailCode": null
}
```

존재하지 않는 기관코드도 같은 형태로 오고 `exists`만 `false`다.

### 규칙

- 기관코드는 영문·숫자 6~8글자다 (`^[A-Za-z0-9]{6,8}$`)
- 프론트엔드는 대문자로 바꿔 보낸다
- 기관코드는 암복호화하지 않는다

### 호출 시점

- 기관코드 확인 화면(`/verify`)에서 입력칸이 채워지는 즉시
- QR 주소 `/verify?orgCode={기관코드}`로 들어와 값이 자동으로 채워진 경우도 같다. 파라미터 키는 대소문자를 가리지 않고 읽는다

### 미해결

- 경기문화재단 기관코드가 아직 서버에 없다. 2026-09-22 기준 `GGCF26`으로 조회하면 `exists: false`다. 실제 코드를 등록하고 값을 알려 주어야 한다

## 4. 계정 발급·재발급

`POST /non-identify/accounts/v1/issue`

### 요청

| 필드    | 타입   | 필수 | 설명                   |
| ------- | ------ | ---- | ---------------------- |
| `orgCd` | string | 예   | 확인을 통과한 기관코드 |

```json
{ "orgCd": "GGCF26" }
```

### 응답

**200 OK**

| 필드            | 타입    | 설명                              |
| --------------- | ------- | --------------------------------- |
| `data.email`    | string  | 발급 아이디. 이메일 형식          |
| `data.password` | string  | 발급 비밀번호                     |
| `data.ttl`      | integer | 남은 시간(초). 절대 시각이 아니다 |

```json
{
  "code": 200,
  "message": "Success",
  "data": {
    "email": "anon-abc123@anon.wdl.kr",
    "password": "Abq17919",
    "ttl": 900
  },
  "detailCode": null
}
```

**400·404·409** — 2장 마절의 에러 코드

### 만료 규칙

- TTL은 15분이고 `ttl`은 초 단위다
- **서버는 만료 시각을 보내지 않는다.** 프론트엔드가 응답을 받은 시각에 `ttl`을 더해 만료 시각을 만들어 표시한다
- TTL은 발급부터 앱 첫 로그인까지만 적용된다. 첫 로그인에 성공한 계정은 만료되지 않는다
- 첫 로그인 없이 만료되면 그 계정으로는 로그인할 수 없다
- 만료 후 재발급 버튼은 두지 않는다. 이용자가 페이지를 새로고침하면 발급 전 상태로 돌아가 새 계정을 받는다

만료 시각을 클라이언트에서 계산하므로 이용자 기기의 시계가 틀리면 표시도 함께 틀어진다. 서버가 절대 시각을 함께 보내 주면 이 문제가 없어진다. `[확인 필요]`

### 재발급 규칙

- 재발급은 같은 API를 다시 호출한다
- 재발급은 이전 계정과 관계없이 새 계정을 만든다. 요청에 이전 계정 정보를 담지 않는다
- 계약 인원 제한이 있어 무제한은 아니다. 초과하면 `CONTRACT005`가 온다

### 아이디·비밀번호 형식

서버가 정한다. 프론트엔드는 받은 값을 그대로 표시한다.

| 필드       | 예시                      |
| ---------- | ------------------------- |
| `email`    | `anon-abc123@anon.wdl.kr` |
| `password` | `Abq17919`                |

아이디가 이메일 형식이라 계정 정보 카드에서 차지하는 폭이 넓다. 화면 문구는 「아이디」를 유지한다.

## 5. 앱 쪽 참고 (웹사이트 범위 밖)

- 만료된 임시 계정으로 앱 로그인을 시도하면 앱이 안내 문구를 보여 준다
- 이 문구와 앱 로그인 API는 이 문서에서 정하지 않는다

## 7. 프론트엔드 mock 규칙

실제 서버를 붙이기 전까지, 그리고 디자인 점검 때 프론트엔드는 mock으로 동작한다. `NEXT_PUBLIC_USE_MOCK=true`일 때만 쓴다.

| 입력                                           | 결과                                    |
| ---------------------------------------------- | --------------------------------------- |
| 유효 기관코드 (환경 변수로 지정, 예: `GGCF26`) | 확인 통과, 계정 발급 성공               |
| 그 밖의 6글자                                  | 확인 실패, 계정 발급 `INVALID_ORG_CODE` |
| 오류 재현용 기관코드 `ERR500`                  | 서버 오류                               |

- mock TTL은 10분이며, 만료 화면을 확인하기 위해 짧게 바꿀 수 있다
- mock 계정은 `wd` + 6자리 형식이라 실제 서버의 이메일 형식과 다르다. 레이아웃을 확인할 때는 실제 서버로 붙여서 본다
