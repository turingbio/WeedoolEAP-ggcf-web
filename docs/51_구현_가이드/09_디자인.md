# 9. 디자인

목표: 8번에서 고정한 구성과 문구 위에 위둘 브랜드 디자인을 입힌다. 자산을 고르고, 시각 방향을 정하고, 토큰과 공통 컴포넌트를 만든 뒤 `/verify`와 `/welcome`에 차례로 적용한다. 정적 화면이 끝나면 모션과 엣지 케이스 화면을 더하고, 접근성을 점검해 DESIGN.md로 정리한다.

- 기준 문서: `docs/42_디자인_배포_인계.md`, `docs/43_디자인_배포_seed.yaml`
- 정본 자산: `docs/40_디자인_자산/`
- 작업 도구: impeccable (`shape`, `critique`, `audit`, `polish`, `document`)
- 작업 분담: 디자인·스타일 코드는 Claude가 구현까지 한다. 이 단계만 "코드는 사용자가 쓴다"는 원칙의 예외다

## 9-1. 무엇을 기준으로 삼나

| 구분      | 대상                                             | 비고                                      |
| --------- | ------------------------------------------------ | ----------------------------------------- |
| 정본      | `DESIGN.md`                                      | 확정된 컨셉·컬러 방향·타이포·모션 규정    |
| 정본      | `src/app/globals.css`, `palette.css`             | 실제로 쓰이는 토큰 값                     |
| 정본      | `40_디자인_자산/41_앱_색상.md`                   | 위둘 앱 색상 팔레트 전체                  |
| 정본      | `40_디자인_자산/brand/`, `character/`, `images/` | 로고, 배너, 톤앤무드, 캐릭터, 편지봉투    |
| 정본      | `docs/21_UX_문구.md` v0.8                        | 구성·순서·문구. 이 단계에서 바꾸지 않는다 |
| 기준 아님 | `90_archive/`의 DESIGN 변형                      | 지난 시안                                 |

`DESIGN.md`와 `globals.css`가 어긋나면 코드가 맞고 문서가 틀린 것으로 본다. `DESIGN.md`는 구현된 값을 기록하는 문서이기 때문이다.

참고 사이트는 runway와 산타 토익 둘로 한정한다. runway에서는 여백과 대비를, 산타 토익에서는 라벨·제목·설명 세 층의 제목 구조와 학습 앱다운 친근함을 본다. 두 사이트는 비교 대상일 뿐이고, 색이나 서체를 가져오지 않는다.

## 9-2. 작업 순서

```
자산 ──▶ 시각 방향 ──▶ 토큰 ──▶ 공통 컴포넌트 ──▶ /verify ──▶ /welcome
                                                                     │
      DESIGN.md ◀── 점검(critique·audit·polish) ◀── 엣지 케이스 ◀── 모션
```

앞 단계가 끝나야 다음 단계의 판단 근거가 생긴다. 토큰 없이 컴포넌트를 만들면 값을 컴포넌트마다 따로 적게 되고, 정적 화면이 끝나기 전에 모션을 넣으면 레이아웃이 바뀔 때마다 모션도 다시 맞춰야 한다.

| 단계 | 산출물             | 끝났다는 기준                              |
| ---- | ------------------ | ------------------------------------------ |
| 9-3  | 받은 자산 목록     | 표의 파일이 `public/`과 `src/app/`에 있다  |
| 9-4  | 정해진 시각 방향   | `DESIGN.md`에 방향과 승인 범위가 적혀 있다 |
| 9-5  | 토큰 세 파일       | 역할 이름을 붙인 토큰만 남았다             |
| 9-6  | 공통 컴포넌트      | 상태별 모양이 모두 정해졌다                |
| 9-7  | 화면 적용          | 375px, 1440px에서 모든 화면이 렌더링된다   |
| 9-8  | 모션               | reduced-motion 대체 표현까지 있다          |
| 9-9  | 엣지 케이스 화면   | 4종 모두 재현 방법이 적혀 있다             |
| 9-10 | 접근성 검증 리포트 | 미해결 위반이 0건이다                      |
| 9-11 | DESIGN.md          | 규정이 실제 구현과 같다                    |

## 9-3. 자산

Figma 원본은 파일이 크고 수가 많아 통째로 읽지 않는다. 필요한 것만 골라 받는다.

### 무엇을 받을지 정하는 기준

앱 디자인을 웹으로 옮길 때 필요한 것은 네 종류다.

| 종류   | 예                       | 없으면 생기는 일                          |
| ------ | ------------------------ | ----------------------------------------- |
| 정체성 | 로고, 캐릭터             | 웹과 앱이 다른 회사처럼 보인다            |
| 규격   | 색, 타이포, 반경, 그림자 | 눈대중으로 정한 값이 화면마다 어긋난다    |
| 형태   | 버튼, 입력창, 카드       | 색은 같은데 모양이 달라 어색하다          |
| 콘텐츠 | 앱 화면 캡처             | 빈 상자로 남아 레이아웃을 확정하지 못한다 |

**값으로 받을 수 있으면 파일로 받지 않는다.** 색은 `41_앱_색상.md`에 헥사값으로 있으니 Figma 색 변수를 다시 받지 않았다. 타이포도 파일이 아니라 숫자 목록으로 받아 `typography.css`에 옮겼다. 파일이 늘어날수록 어느 것이 정본인지 흐려진다.

### 받은 자산

| 자산          | 형식        | 위치                              | 쓰이는 곳                      |
| ------------- | ----------- | --------------------------------- | ------------------------------ |
| 로고 가로형   | PNG 744×128 | `public/brand/logo-full.png`      | Header, Footer, 계정 카드      |
| 파비콘        | PNG         | `src/app/icon.png`                | 브라우저 탭                    |
| 색상 팔레트   | CSS 변수    | `src/app/palette.css`             | `globals.css` 역할 토큰의 원천 |
| 타이포 스케일 | CSS 변수    | `src/app/typography.css`          | 제목·본문 클래스               |
| 히어로 배경   | PNG         | `public/hero-paper-v3.png`        | 01 `hero`                      |
| 기능 일러스트 | PNG 4종     | `public/intro-*.png`              | 02 `intro` 카드                |
| 앱 화면 캡처  | PNG 5종     | `public/screenshot/process-*.png` | 05 `process` 다섯 단계         |
| 캐릭터        | PNG         | `public/character/`               | 보조 요소                      |
| 스토어 배지   | SVG·PNG     | `public/store/`                   | 06 `install`                   |
| 설치 QR       | PNG         | `public/qr/`                      | 06 `install`, 계정 카드        |

로고는 SVG가 아니라 PNG로 받았다. 계정 카드를 PNG로 내보낼 때 `html-to-image`가 화면을 다시 그리므로, 원본 해상도가 표시 크기보다 충분히 커야 저장본에서 로고가 흐려지지 않는다. 744×128은 가장 크게 쓰는 자리의 두 배가 넘어 문제가 없다.

Figma 링크를 주면 Claude가 Figma MCP로 노드 목록을 읽는다. Figma MCP는 인증이 필요하다. 연결되지 않으면 `claude mcp`로 인증부터 한다.

## 9-4. 시각 방향

### 화면 성격 먼저 나누기

impeccable은 화면의 목적에 따라 판단 기준을 바꾼다. 두 화면은 목적이 다르다.

| 화면       | 방문자가 하는 일              | 성격     | 우선하는 것              |
| ---------- | ----------------------------- | -------- | ------------------------ |
| `/verify`  | 기관코드를 넣고 통과한다      | Operate  | 빠른 인지, 오류의 명확함 |
| `/welcome` | 읽고, 안심하고, 계정을 받는다 | Persuade | 신뢰, 리듬, 섹션 간 위계 |

`/verify`에 랜딩의 장식을 그대로 가져오면 입력칸이 묻힌다. 두 화면은 같은 토큰을 쓰되 밀도를 다르게 둔다.

### 정해진 방향

```
/impeccable shape /welcome
```

`shape`는 `PRODUCT.md`와 `docs/21_UX_문구.md`를 읽고 시각 방향을 2~3안 만든다. 각 안은 이름, 한 줄 요약, 대표 화면(Hero와 03 익명성) 두 장으로 비교한다. 섹션 전체를 그리지 않는다. 두 섹션이면 방향 차이가 드러나고, 전체를 그리면 고르기 전에 하루가 간다.

고른 결과와 이유는 `DESIGN.md`에 있다. 2장이 컨셉과 무드, 6장이 Hero 기준, 7장이 기능 소개 배치다. 별도의 시안 비교 문서는 만들지 않았고, 승인 범위와 미확정 사항까지 `DESIGN.md` 12장에 함께 적었다. 방향을 다시 물을 일이 생기면 이 문서를 본다.

## 9-5. 디자인 토큰

토큰은 세 파일로 나눠 둔다. 섞어 두면 앱에서 온 값과 웹에서 정한 값을 구분할 수 없다.

| 파일             | 담는 것                                 | 고치는 때               |
| ---------------- | --------------------------------------- | ----------------------- |
| `palette.css`    | 앱 팔레트 원본 값                       | 앱 색상이 바뀔 때만     |
| `typography.css` | 앱 타이포 스케일                        | 앱 타이포가 바뀔 때만   |
| `globals.css`    | 역할 이름을 붙인 웹 토큰, 공통 레이아웃 | 웹에서 쓰임새가 바뀔 때 |

`globals.css`는 `@theme inline`을 쓴다. `palette.css`의 변수를 참조하는 토큰이 있어서 `inline`이 필요하다.

### 색

원본 팔레트를 그대로 쓰지 않고 역할 이름을 붙여 옮긴다. 쓰지 않는 토큰은 나중에 누군가 "이것도 써도 되나" 고민하게 만든다.

| 토큰             | 값        | 흰 바탕 대비 | 쓰는 곳                       |
| ---------------- | --------- | ------------ | ----------------------------- |
| `brand`          | `#008eff` | 3.33         | 포커스 링, 큰 글자 강조, 장식 |
| `brand-bright`   | `#0066ff` | 4.83         | 주 버튼 배경                  |
| `brand-strong`   | `#0066ff` | 4.83         | 버튼 눌림, 보조 버튼 글자     |
| `brand-link`     | `#0052cc` | 6.82         | 라벨(eyebrow), 버튼 호버      |
| `brand-mid`      | `#003d99` | 9.87         | 헤더 버튼 호버                |
| `brand-deep`     | `#002966` | —            | 짙은 배경 면                  |
| `brand-soft`     | `#edf4fc` | —            | 선택 영역 배경                |
| `brand-tint`     | `#f1f6fc` | —            | 보조 버튼 호버 배경           |
| `brand-pale`     | `#e5efff` | —            | 섹션 그라데이션 시작          |
| `ink`            | `#202b37` | 14.36        | 제목, 본문                    |
| `subtle`         | `#344051` | 10.51        | 보조 제목                     |
| `muted`          | `#414e62` | 8.43         | 설명 문장                     |
| `line`           | `#e4e9ef` | —            | 구분선                        |
| `control-border` | `#d9dee6` | —            | 입력칸 테두리                 |
| `surface`        | `#faf8f4` | —            | 종이 느낌 배경 면             |
| `danger`         | `#e31c41` | 4.66         | 오류 문장                     |

골라낸 기준이 몇 가지 있다.

- **주 버튼 배경은 Normal(`#008eff`)이 아니라 `#0066ff`를 쓴다.** Normal은 흰 바탕 대비가 3.33이라 흰 글씨 버튼과 본문 링크에서 4.5:1을 넘지 못한다. Normal은 포커스 링이나 장식처럼 글자가 아닌 곳에 둔다.
- **오류색은 Negative(`#f64c4c`)가 아니라 `--palette-red-crayola-600`(`#e31c41`)을 쓴다.** Negative는 대비가 3.47이다.
- **토큰 이름은 앱 이름을 따르지 않고 역할로 짓는다.** `41_앱_색상.md`에서 가장 진한 글자색이 `label-secondary`이고 `label-primary`가 그보다 옅어, 이름을 그대로 가져오면 헷갈린다.
- **`cool-neutral-70` 이하(`#878a93`, `#aeb0b6`)는 글자에 쓰지 않는다.** 대비가 각각 3.45, 2.17이다.

새 색을 토큰에 더할 때는 먼저 흰 바탕과 해당 배경에서 대비를 재고, 4.5:1을 넘지 못하면 글자에 쓰지 않는다. 브랜드 색을 지키느라 넘기지 못하는 자리가 생기면 억지로 색을 바꾸지 말고, 위치와 사유를 9-10의 리포트에 적는다.

### 타이포·간격

서체는 Pretendard Variable을 쓴다. 단계별 크기는 `typography.css`의 앱 스케일을 따르고, 아래 값은 규격과 상관없이 지킨다.

| 항목      | 값        | 근거                                  |
| --------- | --------- | ------------------------------------- |
| 본문 글자 | 16px 이상 | 주 사용자에 고연령층이 있다           |
| 버튼 글자 | 14px 이상 | `DESIGN.md` 5장                       |
| 터치 영역 | 48px 이상 | 버튼을 작게 보이되 누르기 쉽게 만든다 |

버튼 글자가 본문보다 작은 것은 의도한 결정이다. `DESIGN.md` 5장이 "버튼의 작은 시각적 크기와 충분한 터치 영역을 양립시킨다"로 적고 있다. 글자를 키우는 대신 `min-h-touch`로 누를 수 있는 넓이를 확보한다.

### 공통 레이아웃 클래스

토큰 외에 `globals.css`의 `@layer components`에 네 가지를 둔다. 섹션마다 같은 여백을 다시 적지 않기 위한 것이다.

| 클래스                         | 하는 일                                      |
| ------------------------------ | -------------------------------------------- |
| `.site-container`              | 최대 1280px, 좌우 여백 20px(768px 이상 32px) |
| `.section-shell`               | 섹션 위아래 여백 48px(768px 이상 120px)      |
| `.section-heading`             | 라벨·제목·설명 묶음의 정렬과 아래 여백       |
| `.eyebrow`, `.editorial-title` | 라벨과 제목의 크기·굵기·자간                 |

## 9-6. 공통 컴포넌트

화면보다 컴포넌트를 먼저 만든다. 버튼 하나가 네 섹션에 쓰이니, 섹션마다 스타일을 적으면 같은 버튼이 네 가지 모양이 된다.

| 컴포넌트         | 파일                                    | 상태                             |
| ---------------- | --------------------------------------- | -------------------------------- |
| `Button`         | `src/components/ui/Button.tsx`          | 기본, 호버, 눌림, 포커스, 비활성 |
| `ButtonLink`     | `src/components/ui/Button.tsx`          | 같은 모양을 `<a>`로 쓸 때        |
| `SectionWrapper` | `src/components/SectionWrapper.tsx`     | 라벨 있음/없음, 설명 있음/없음   |
| 기관코드 입력칸  | `src/features/org-code/OrgCodeForm.tsx` | 기본, 포커스, 오류, 확인 중      |

`Button`은 모양 세 가지와 크기 두 가지를 조합한다.

| 구분 | 값          | 쓰는 곳                     |
| ---- | ----------- | --------------------------- |
| 모양 | `primary`   | 계정 발급 같은 주 행동      |
| 모양 | `secondary` | 이미지로 저장처럼 보조 행동 |
| 모양 | `ghost`     | 테두리만 있는 약한 행동     |
| 크기 | `md`        | 기본. 최소 높이 48px        |
| 크기 | `lg`        | 섹션 안의 큰 CTA            |

카드에는 공통 컴포넌트를 두지 않았다. 02 기능 카드, 03 익명성 카드, 계정 정보 카드가 모양과 목적이 각각 달라, 하나로 묶으면 옵션만 늘어나기 때문이다. 같은 모양이 세 번째로 필요해지면 그때 묶는다.

모든 상호작용 요소는 포커스가 보여야 한다. 마우스로 쓸 때는 보이지 않다가 키보드로 옮겨 올 때만 나타나도록 `focus-visible`을 쓴다. 비활성 상태는 투명도를 낮추는 대신 `disabled` 전용 배경색과 글자색을 둔다. 투명도만 낮추면 배경에 따라 대비가 들쭉날쭉해진다.

`SectionWrapper`는 8번에서 정한 세 층(라벨·제목·설명)을 한 곳에서 그린다. 섹션 컴포넌트가 제목 크기나 라벨 색을 따로 정하지 않게 하려는 것이다.

## 9-7. 화면 적용

`/verify` → Header → 01~07 → Footer 순으로 적용한다. 한 화면을 끝낼 때마다 375px와 1440px에서 확인한다.

| 화면·섹션      | 디자인에서 볼 것                                                       |
| -------------- | ---------------------------------------------------------------------- |
| `/verify`      | 입력칸이 첫눈에 들어오는가. 오류 문장이 입력칸 바로 아래에 붙는가      |
| Header         | 로고와 계정 발급 버튼. 내릴 때 숨고 올릴 때 다시 나온다                |
| 01 `hero`      | 종이 질감 배경과 잔잔한 빛. 계정 발급 CTA 하나                         |
| 02 `intro`     | 라벨·제목·설명 위계. 기능 카드 2×2(모바일 1열)                         |
| 03 `anonymity` | 카드 3개. 모바일에서 세로로 쌓인다                                     |
| 04 `account`   | 발급 전·중·후·오류 네 상태의 높이 차이로 화면이 튀지 않는가            |
| 05 `process`   | 캡처 5장의 표시 크기가 같은가. 칸 테두리 없이 여백과 번호로 구분되는가 |
| 06 `install`   | QR 두 개와 스토어 배지. 모바일에서는 QR보다 배지가 먼저                |
| 07 `faq`       | 질문을 누르면 답이 펼쳐진다. 펼친 질문이 눈에 띈다                     |
| Footer         | 짙은 배경 위 대비. 전화·메일 링크가 48px 터치 영역을 갖는다            |

06 설치에서 모바일에 배지를 먼저 두는 것은, 휴대폰으로 들어온 사람이 자기 화면의 QR을 찍을 수 없기 때문이다.

Header가 스크롤 방향에 따라 숨는 것은 본문을 읽는 동안 화면을 넓게 쓰기 위한 것이다. 최상단 80px 안에서는 항상 보이고, 6px 미만의 작은 움직임에는 반응하지 않아 깜빡이지 않는다.

## 9-8. 인터랙션·모션

정적 화면이 모두 끝난 뒤에 넣는다.

```
/impeccable animate /welcome
```

`DESIGN.md` 8장이 정한 방향은 잔잔하게 이어지는 움직임이다. 배경의 빛이나 장식이 천천히 변하는 정도이고, 글자와 버튼의 위치는 고정한다. 기존 봉투 스프라이트는 재사용하지 않는다.

| 대상             | 움직임                                          | reduced-motion일 때 |
| ---------------- | ----------------------------------------------- | ------------------- |
| Hero 빛 입자     | `hero-twinkle` — 4.2초 주기로 밝기와 크기 변화  | 멈춘 상태로 보인다  |
| Hero 반짝임      | `hero-sparkle` — 5초 주기로 나타났다 사라짐     | 멈춘 상태로 보인다  |
| Hero 떠오름      | `hero-float` — 7초 주기로 위아래 14px           | 멈춘 상태로 보인다  |
| Header           | 스크롤 방향에 따라 0.3초 미끄러짐               | 바로 자리를 잡는다  |
| 버튼             | 호버·눌림 시 색이 0.2초에 걸쳐 진해진다         | 색 변화만 유지한다  |
| 계정 발급 중     | 버튼 문구가 「계정을 생성하고 있어요」로 바뀐다 | 같다                |
| 기관코드 확인 중 | 입력칸 옆 회전 표시                             | 회전을 멈춘다       |
| FAQ              | 답이 펼쳐진다                                   | 바로 펼쳐진다       |

같은 박자로 깜빡이지 않도록 입자마다 `animation-delay`를 다르게 준다.

움직임은 한 곳에서 모두 끈다. 섹션마다 따로 막으면 하나를 빠뜨린다.

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation: none !important;
    transition: none !important;
    scroll-behavior: auto !important;
  }
}
```

`animation: none`으로 끄면 요소는 애니메이션이 없는 본래 모습으로 남는다. 첫 프레임이 투명한 장식은 reduced-motion에서 보이지 않게 되므로, 없어도 화면이 성립하는 장식에만 그런 움직임을 준다.

## 9-9. 엣지 케이스 화면

네 가지 실패 상태를 화면으로 만들고, 재현 방법을 함께 적는다. 재현 방법이 없으면 디자인을 확인할 때마다 실패가 일어나기를 기다려야 한다.

| 상태           | 화면                        | 문구 위치                           | mock 재현 방법                        |
| -------------- | --------------------------- | ----------------------------------- | ------------------------------------- |
| 기관코드 오류  | `/verify` 입력칸 아래       | `common.ts` `errors.invalidOrgCode` | 유효 기관코드가 아닌 6글자 입력       |
| 네트워크 오류  | `/verify` 입력칸 아래       | `common.ts` `errors.network`        | 기관코드 `ERR500` 입력                |
| 계정 발급 실패 | 04 `account` 버튼 위        | `account/content.ts` `issueError`   | 개발자 도구 Network 탭을 Offline으로  |
| PNG 저장 실패  | 04 `account` 계정 카드 아래 | `common.ts` `errors.network`        | 카드 안 이미지 경로를 일부러 깨뜨린다 |

`ERR500`은 `src/lib/api/mock/org.ts`에 정해 둔 값이다. 유효 기관코드는 `NEXT_PUBLIC_MOCK_VALID_ORG_CODE`로 바꾼다.

PNG 저장 실패는 문구를 새로 만들지 않고 `errors.network`를 쓴다. 이용자가 할 일이 「다시 시도한다」로 같기 때문이다. 이 화면은 검증 스크립트에서 이미지 로드 실패를 주입해 확인했고, 기록은 `docs/45_접근성_검증.md`에 있다.

## 9-10. 점검과 접근성 검증 리포트

정적 화면, 모션, 엣지 케이스까지 모두 들어간 뒤에 한 번에 점검한다.

```
/impeccable critique /welcome
/impeccable audit
/impeccable polish
```

`critique`는 위계와 흐름을, `audit`은 대비·키보드·반응형 같은 기술 항목을 본다. 두 결과를 모아 `polish`로 한꺼번에 고친다. 항목마다 고치고 다시 점검하기를 반복하면 끝이 나지 않는다. 모바일과 데스크톱 스크린샷을 한 번에 찍어 보고, 고친 뒤 한 번만 더 확인한다.

impeccable의 자동 탐지 훅은 설정에 등록되어 있지 않다. 파일을 고쳐도 저절로 점검하지 않으니 `audit`을 직접 실행한다.

| 항목           | 기준                                       |
| -------------- | ------------------------------------------ |
| 텍스트 대비    | 4.5:1 이상. 24px 이상 큰 글자는 3:1 이상   |
| 키보드 조작    | Tab만으로 `/verify` → 계정 발급 → 설치까지 |
| 포커스 표시    | 모든 상호작용 요소에서 보인다              |
| 글자 크기      | 본문 16px 이상, 버튼 14px 이상             |
| 터치 영역      | 48px 이상                                  |
| 글자 확대      | 200%에서 겹치거나 잘리지 않는다            |
| reduced-motion | 9-8 표의 대체 표현이 나온다                |

결과는 `docs/45_접근성_검증.md`에 남긴다. 미해결 위반은 0건이어야 하고, 브랜드 색 때문에 남긴 위반만 위치와 사유를 적어 예외로 둔다. 리포트에는 확인하지 못한 범위도 함께 적는다. 실기기 카메라로 QR을 찍어 보는 것처럼 로컬에서 할 수 없는 항목은 10번 문서의 실기기 점검으로 넘긴다.

## 9-11. DESIGN.md

`DESIGN.md`는 저장소 루트에 둔다. 인터뷰에서 확정한 컨셉·컬러 방향·타이포·모션 규정과, 아직 확정하지 않은 범위를 함께 적는다. impeccable의 `document`로 초안을 뽑을 수 있지만, 사용자가 승인한 것과 시안에 우연히 들어간 요소를 가르는 일은 자동으로 되지 않는다. 12장에 승인 범위가 아닌 것을 따로 적어 두는 이유다.

화면을 고친 뒤에는 `DESIGN.md`의 규정이 실제 구현과 맞는지 본다. 로고 파일이나 헤더 구성처럼 문서가 먼저 적어 둔 것이 구현에서 달라졌다면, 코드가 맞고 문서가 틀린 것으로 보고 문서를 갱신한다.
