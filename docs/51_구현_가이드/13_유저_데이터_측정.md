# 13. 유저 데이터 측정

목표: 몇 명이 들어와서 어디까지 갔는지 알 수 있게 Google Analytics 4를 붙인다. 무엇을 볼지 먼저 정하고, 그 질문에 답하는 이벤트만 심는다.

---

## 13-1. 언제 붙이나

기준은 개발이 끝난 시점이 아니라 실사용자가 들어오기 직전이다.

첫 배포와 동시에 붙어 있어야 초기 유입을 놓치지 않는다. 한참 뒤에 붙이면 서비스 초기 몇 주치가 통째로 비는데, 보통 그 구간이 가장 궁금하다. 반대로 개발 중에 붙여 두면 테스트하며 누른 클릭이 실제 지표에 섞이고, 화면이 바뀔 때마다 이벤트도 따라 흔들린다.

| 하는 일                        | 시점                  |
| ------------------------------ | --------------------- |
| 무엇을 볼지 정하기             | 언제든. 문서 작업이다 |
| 컴포넌트 연결과 환경 변수 자리 | 배포 준비와 함께      |
| 이벤트 심기                    | 화면이 굳은 뒤        |
| 측정 ID를 운영 환경에 넣기     | 배포와 동시에         |

이벤트 이름은 한 번 내보내면 되돌리기 번거롭다. GA4는 이름을 바꿔도 이전 이름으로 쌓인 데이터와 합쳐 주지 않아, 보고서에서 두 지표를 손으로 이어 봐야 한다.

---

## 13-2. 무엇을 볼지 먼저 정한다

클릭할 수 있는 곳을 전부 이벤트로 만들면 보고서만 복잡해지고 정작 궁금한 것은 답이 안 나온다. 질문을 먼저 적고, 각 질문에 답하는 데 필요한 이벤트만 남긴다.

이 사이트에서 답이 궁금한 질문은 다음과 같다.

| 질문                                          | 알면 무엇을 하나                        |
| --------------------------------------------- | --------------------------------------- |
| 기관코드를 확인한 사람 중 몇 명이 계정을 받나 | 계정 발급 섹션의 위치와 문구를 판단한다 |
| 기관코드 입력에서 막히는 사람이 얼마나 되나   | 6칸 입력 방식이 쓸 만한지 판단한다      |
| 계정을 받고도 앱 설치로 가지 않는 비율은      | 설치 안내를 더 위로 올릴지 판단한다     |
| 계정 정보 카드를 실제로 챙겨 가나             | 자동 저장이 제 역할을 하는지 판단한다   |
| 매뉴얼을 받아 가는 사람이 있나                | 매뉴얼 버튼을 유지할지 판단한다         |

경기문화재단에 보고할 숫자가 정해져 있다면 그 숫자부터 역산하는 편이 빠르다.

---

## 13-3. 이벤트 설계

위 질문에 답하는 이벤트는 여섯 개다.

| 이벤트명            | 언제                      | 파라미터                                                      |
| ------------------- | ------------------------- | ------------------------------------------------------------- |
| `cta_account_click` | 계정 발급 CTA 클릭        | `location`: `header` \| `hero`                                |
| `org_code_checked`  | 기관코드 확인 결과가 나옴 | `result`: `ok` \| `invalid` \| `error`                        |
| `account_issued`    | 계정 발급 성공·실패       | `result`: `success` \| `error`                                |
| `credential_saved`  | 계정 카드 저장 결과       | `trigger`: `auto` \| `manual`, `result`: `success` \| `error` |
| `store_click`       | 스토어 배지 클릭          | `store`: `ios` \| `android`                                   |
| `manual_download`   | 매뉴얼 내려받기           | 없음                                                          |

GA4는 이벤트명을 snake_case로 쓰고 40자까지 받는다.

이름과 파라미터는 `src/lib/analytics.ts` 한 곳에 타입으로 묶는다. 이름만 상수로 뽑으면 파라미터 키가 여전히 갈라진다. 한 곳에서 `result`를 보내고 다른 곳에서 `status`를 보내면 GA에서는 서로 다른 측정기준이 된다.

```ts
type EventParams = {
  cta_account_click: { location: 'header' | 'hero' };
  org_code_checked: { result: 'ok' | 'invalid' | 'error' };
  ...
};

export function trackEvent<T extends keyof EventParams>(name: T, ...args: EventArgs<T>) {
  sendGAEvent('event', name, ...args);
}
```

이렇게 두면 이벤트명을 잘못 적거나 없는 값을 넣었을 때 타입 검사에서 걸린다. 측정 코드는 화면에 아무것도 드러내지 않아서 틀려도 조용히 틀린다.

### 나중에 더할 만한 것

기관코드를 몇 번 만에 통과했는지는 지금 설계로 알 수 없다. 시도마다 결과가 한 건씩 찍힐 뿐이라 한 번에 맞힌 사람과 네 번 틀린 사람이 구분되지 않는다. 6칸 입력 방식을 평가하려면 `org_code_checked`에 시도 횟수를 파라미터로 더한다. 처음부터 넣지 않는 이유는, 세션 안에서 횟수를 세는 상태가 하나 늘기 때문이다. 필요해지면 그때 넣는다.

## 13-4. 설치와 연결

```bash
pnpm add @next/third-parties@latest
```

측정 ID는 환경 변수로 둔다. `.env.example`에 빈 항목을 넣고 실제 값은 `.env.local`과 배포 환경 변수에만 둔다.

```
# GA4 측정 ID (G-로 시작). 비워 두면 GA를 싣지 않음
NEXT_PUBLIC_GA_ID=
```

`src/app/layout.tsx`의 `</body>` 뒤, `</html>` 안쪽에 컴포넌트를 넣는다. 값이 없으면 아무것도 렌더링하지 않아야 로컬 개발 트래픽이 섞이지 않는다.

```tsx
<body className="flex min-h-full flex-col">
  <FlowProvider>{children}</FlowProvider>
</body>;
{
  gaId ? <GoogleAnalytics gaId={gaId} /> : null;
}
```

페이지뷰는 따로 손대지 않아도 잡힌다. 클라이언트 라우팅도 브라우저 히스토리 변화를 감지해 기록한다.

이벤트를 심는 자리는 `Header.tsx`, `HeroSection.tsx`, `OrgCodeForm.tsx`의 `applyResult`, `AccountSection.tsx`의 `handleIssue`, `CredentialPanel.tsx`의 `saveImage`, `InstallSection.tsx`다. `applyResult`와 `saveImage`는 자동 실행과 수동 클릭이 모두 거쳐 가는 한 곳이라, 여기에 넣으면 QR 진입과 직접 입력이 함께 잡힌다.

## 13-5. GA 콘솔 설정

### 콘솔 주소

이 프로젝트의 데이터 스트림 화면이다. 측정 ID는 여기 오른쪽 위에 있다.

<https://analytics.google.com/analytics/web/#/a240809802p331541364/admin/streams/table/15822627032>

### 측정 ID 발급

관리(왼쪽 아래 톱니) → 데이터 수집 및 수정 → 데이터 스트림 → 웹 스트림을 만든다. 스트림에 적는 URL은 수집 범위를 제한하지 않고 사실상 라벨이라, 도메인이 정해지기 전이라도 임시로 넣고 나중에 고쳐도 된다.

### 향상된 측정

스트림 세부정보의 향상된 측정에서 "브라우저 기록 이벤트를 기반으로 하는 페이지 변경"에 체크가 되어 있는지 본다. 꺼져 있으면 `/`에서 `/welcome`으로 넘어가는 이동이 페이지뷰로 잡히지 않는다.

### 맞춤 측정기준

이 단계를 빼먹으면 이벤트 횟수만 보이고 `result`나 `location` 값은 보고서에서 쪼갤 수 없다. **등록 시점 이후에 수집된 데이터부터 적용되고 과거에는 소급되지 않는다.** 배포 전에 미리 만든다.

관리 → 데이터 표시 → 맞춤 정의에서 범위를 이벤트로 두고 등록한다.

| 측정기준 이름 | 이벤트 매개변수 |
| ------------- | --------------- |
| result        | `result`        |
| location      | `location`      |
| store         | `store`         |
| trigger       | `trigger`       |

## 13-6. 검증

관리 → 데이터 표시 → DebugView에서 이벤트가 들어오는지 본다. 디버그 모드는 컴포넌트 속성으로 켠다.

```tsx
<GoogleAnalytics gaId={gaId} debugMode={process.env.NODE_ENV !== 'production'} />
```

확인할 동선은 다음과 같다.

1. 헤더와 히어로의 CTA를 각각 눌러 `location`이 갈리는지
2. 기관코드를 틀리게 넣어 `result`가 `invalid`로 오는지
3. 계정 발급, 카드 저장, 스토어 배지, 매뉴얼이 각각 잡히는지
4. 어느 이벤트에도 기관코드 값이나 계정 정보가 실려 있지 않은지

검증이 끝나면 `.env.local`의 측정 ID를 다시 비운다. 그러지 않으면 개발하며 누른 클릭이 계속 실제 지표에 섞인다. 자주 확인할 일이 생기면 개발용 GA4 속성을 따로 만들어 로컬에서는 그쪽으로 보낸다.

사무실 고정 IP가 있으면 스트림 세부정보 → 태그 설정 구성 → 내부 트래픽 정의에 규칙을 만들고, 데이터 필터에서 내부 트래픽 제외를 활성 상태로 바꾼다.

## 13-7. 개인정보

`docs/11_seed.yaml`의 제약은 개인을 식별할 수 있는 값을 일절 수집·전송하지 않는 것이다. 측정 코드도 이 제약 안에 있다.

- 기관코드 값을 파라미터로 보내지 않는다. 성공·실패 여부만 보낸다. 기관을 특정하는 식별자다
- 발급된 아이디·비밀번호를 어떤 이벤트에도 싣지 않는다
- 화면에 입력한 값을 자동으로 수집하는 태그를 쓰지 않는다

GTM을 쓰지 않고 GA4를 직접 연동하는 이유도 여기에 있다. 태그 관리자를 쓰면 콘솔 권한을 가진 사람이 나중에 입력값을 수집하는 태그를 넣을 수 있고, 무엇이 실제로 실행되는지 코드만 봐서는 알 수 없다. 직접 연동하면 수집 지점이 전부 저장소에 드러난다.

마케팅 태그를 계속 얹을 계획이 생기면 그때 GTM으로 옮겨도 늦지 않다.
